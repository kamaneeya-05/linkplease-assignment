# LinkPlease — Failures

## Remaining Failure Modes and Edge Cases

- **Transient 404s Mark Deliveries as Terminally Failed**: When checking the status of a sent DM, if the API returns a temporary 404 (due to replica sync lag or database lag on their side), our system raises a permanent error. The worker immediately marks the delivery as permanently `FAILED`. This can cause us to lose a DM (if it actually failed and needed a retry) and report an incorrect `/stats` count.
- **Database Failures Post-API-Dispatch Send Duplicate DMs**: If the worker successfully sends a DM to the API but the database commit to mark it as `SENT` fails or times out, the local transaction rolls back and the delivery stays `QUEUED`. If the worker retries sending after the API's idempotency cache has already cleared, the API will accept the retry as a new request and send a duplicate DM.
- **Event ID Collisions Skip Comment Deletions**: Because `event_id` has a global unique constraint in our database, if the API uses the same event ID for both a creation and a deletion event, the deletion event is blocked with an integrity error. The system logs it as a duplicate and ignores it, meaning we will fail to cancel the pending DM and send an unwanted message.
- **Delete Event Races After DM Dispatch Send Unwanted DMs**: If a user deletes a comment after the worker has already dispatched the DM to the API (status is `SENT`), the incoming `comment.deleted` event is ignored because we only allow cancellation of `PENDING` or `QUEUED` jobs. The user will still receive the DM even though the comment was deleted before the DM arrived in their inbox.
